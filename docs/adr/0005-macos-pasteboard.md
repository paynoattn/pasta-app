# 0005. macOS: pasteboard polling, own-write markers, Universal Clipboard bridge

- Status: Accepted (verified on an Apple Silicon Mac with an iPhone; one follow-up check
  for password-manager browser extensions moves to #36)
- Date: 2026-10-23
- Issue: #6 (spike)

## Context

macOS has no public "clipboard changed" notification. Pasta must notice copies cheaply,
skip password-manager items, recognise its own writes, record the source app for the
panel's icon, and (optionally) bridge iCloud Universal Clipboard so iPhone/iPad copies
reach the tailnet and vice versa.

## Decision

- **Watch** by polling `NSPasteboard.generalPasteboard.changeCount` every **250 ms** on a
  background thread with a run loop; read types only when the count changes. This is
  the approach clipboard managers (including Paste.app) use.
- **Read** `public.utf8-plain-text`, `public.html`, `public.rtf`.
- **Skip sensitive items in three ways**, because password managers don't reliably mark
  their copies (see findings):
  1. items carrying the nspasteboard.org markers `org.nspasteboard.ConcealedType`,
     `org.nspasteboard.TransientType` or `org.nspasteboard.AutoGeneratedType`;
  2. a **built-in, user-editable list of password-manager apps** by bundle id, on by
     default (confirmed: Proton Pass `me.proton.pass.electron`, Apple Passwords
     `com.apple.Passwords`; to research: 1Password, Bitwarden, KeePassXC, Keychain
     Access, Dashlane, Enpass);
  3. **password-manager browser extensions**, recognised by an `org.chromium.source-url`
     whose origin is `chrome-extension://<id>` for a known extension id (#36).
- **Mark own writes** with a custom type `dev.pasta.origin`, **and** keep a short-lived
  set of content hashes Pasta wrote. Don't rely on the marker alone: it may not survive
  Universal Clipboard.
- **Source app** = `NSWorkspace.frontmostApplication` at the moment the change is seen
  (name + bundle id → icon cache in #37).
- **Universal Clipboard items** carry `com.apple.is-remote-clipboard` (confirmed). Label
  them "iPhone · iCloud" from that flag, **never from the frontmost app**, which is just
  whatever happened to be in front on the Mac. Treat them as local copies to broadcast (#41).
- **Drop back-to-back duplicates** before broadcasting: a change whose content hash
  matches the previous local item within a few seconds is not a new copy (#16).

## Findings so far

`mac_pasteboard_probe -- watch 120` on an Apple Silicon Mac, polling every 250 ms:

- Copies from Microsoft Teams, Brave and iTerm2 were all picked up, each with the
  **correct frontmost app** (name + bundle id).
- **Formats vary by app.** Teams (Chromium-based) provided `public.html`,
  `Apple HTML pasteboard type`, `public.utf8-plain-text`, `NSStringPboardType`,
  `org.chromium.internal.source-rfh-token` and `org.chromium.source-url`. The Brave and
  iTerm2 copies carried plain text only (`public.utf8-plain-text` plus the legacy
  `NSStringPboardType` alias).
- **The same text often arrives twice.** Teams produced two changes 1.8 s apart and iTerm2
  two changes 1 s apart, with identical lengths. Whether they come from repeated copies or
  from the app writing twice (e.g. iTerm2 copy-on-select), the engine must not broadcast
  the second one (decision above).
- `org.chromium.source-url` gives the page a Chromium-based app copied from at no cost: a
  candidate for link cards in the Mac panel (#40).

Second run (password managers and iPhone):

- **Proton Pass does not mark copies as sensitive.** A copy from the desktop app
  (`me.proton.pass.electron`) carried only `public.utf8-plain-text` and
  `NSStringPboardType`, with no concealed/transient marker. Pasta would have synced the
  password, hence the app and extension lists in the decision.
- **Neither does Apple's own Passwords app** (`com.apple.Passwords`): a copied password
  carried only `public.utf8-plain-text` and `NSStringPboardType`. The nspasteboard.org
  markers can't be the main defence on macOS.
- **The Proton Pass Chrome extension (in Brave) looks like an ordinary Brave copy:** plain
  text plus `org.chromium.source-url`, frontmost app Brave. App-based exclusion can't
  catch it. The probe now prints the source URL's origin (scheme + host only) to confirm
  it shows `chrome-extension://<id>`.
- **A copy made on the iPhone arrived with `com.apple.is-remote-clipboard`** and rich
  formats: `iOS rich content paste pasteboard type`, `com.apple.webarchive`,
  `public.html`, `public.utf8-plain-text`, `public.text`,
  `com.apple.WebKit.custom-pasteboard-data`. The frontmost app at that moment was
  unrelated (Teams).
- **Mac → iPhone works for normal copies and for Pasta's own writes.** After
  `mac_pasteboard_probe -- write`, which writes from a command-line process with no
  window, pasting on the iPhone gave `pasta-spike-marker`. Programmatic writes do reach
  Universal Clipboard, so the bridge (#41) can be write-based.
- **The own-write marker does not survive Universal Clipboard.** Copying the pasted
  marker again on the iPhone brought it back to the Mac with `universal_clipboard=true`
  and `pasta_marker=false`, reduced to `public.utf8-plain-text`, `NSStringPboardType`,
  `public.text` and `com.apple.is-remote-clipboard`. Same result as Win+V (ADR 0004):
  **echo prevention must use content hashes**; the marker only helps for the immediate
  local write.

## To confirm on hardware

Run on a Mac:
`cargo run -p pasta-clipboard --example mac_pasteboard_probe -- watch 120`, then
`… -- write 120`, and record:

- [x] CPU use of 250 ms polling while idle: **~0.1% CPU**, 3 threads, ~4 idle wake-ups
      in Activity Monitor (debug build). Negligible, so keep 250 ms.
- [x] Password managers: Proton Pass (app and extension) and Apple Passwords do **not**
      set a concealed marker.
- [ ] Proton Pass extension: `chromium source origin` shows `chrome-extension://<id>`
      (follow-up in #36; needs the updated probe on the Mac).
- [ ] 1Password / Bitwarden / Keychain Access (later; no accounts yet).
- [x] Frontmost app is correct when copying from different apps (see findings).
- [x] A copy on an iPhone appears on the Mac and carries `com.apple.is-remote-clipboard`.
- [x] A normal Mac copy can be pasted on the iPhone.
- [x] `write` mode: the probe's item reaches the iPhone (programmatic writes propagate
      through Universal Clipboard).
- [x] After a round trip (Mac → iPhone → copy again on iPhone → Mac), `dev.pasta.origin`
      is gone, so hash dedupe is required.

## Consequences

- Polling costs a little CPU; 250 ms keeps perceived latency low.
- Universal Clipboard only reaches nearby devices and expires after about 2 minutes;
  Pasta can't change that.
